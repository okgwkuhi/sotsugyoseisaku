3. 課題の整理（表面的になっていないか）
3-1. 表に見えている困りごと
表面的な出会いでは満たされない(深く趣味を語れる相手ではないと満足できない)

3-2. 本当に解決したい課題は何か
「断られる・温度差を感じるかもしれない」という不安から、誘う・つながり続ける行動そのもの化が止まってしまうこと

・「初心者だから参加しづらい」→ 温度差の不安があるから、初心者であることを伝えて配慮を求めること自体に抵抗が生まれる
・「知らない人に声をかけづらい」→ 温度差の不安があるから、声をかける前に「今回もズレるかも」と身構えてしまう
・「一度会った人と継続できない」→ 温度差の不安があるから、良かった相手にすら「また遊ぼう」と言い出せない

他の3つの困りごとは特定の場面(初参加時・声かけ時・母数不足時)に限定された障壁であるのに対し、「温度差を感じるかもしれない不安」は行動のあらゆる場面(初参加・声かけ・継続)に共通して効いてくる、行動全体を止めるブレーキです。だからこそ、これを解消することが、他の3つの困りごとの解消にも波及する、最も優先度の高い課題だと考えられる。

5-2. それでも自分が作りたい理由
ボドゲゴーには会も住み分けもすでにあり、「もう十分では」と思う瞬間もあった。それでも満足できなかったのは、「良かった出会いを、その日限りで終わらせたくない」という一点だった。良い出会いがあっても、また会いたいと思ったとき自分から連絡する手段がなく、結局「また会に来るかどうか」という偶然任せになる。

掘り下げると、これは機能不足ではなく、自分が「誘う」という行為にずっと及び腰だったことに気づいた。良かった相手にすら「また遊びたい」と言い出せない。断られる不安が、相手が好意的でも拭えなかった。既存サービスは「出会う場」は作っても、この「誘う一歩」の重さには触れていない。

だから作りたいのは掲示板や温度感タグではなく、「もう一度会いたいと思ったとき、リスクなくそれを伝えられる仕組み」。これが自分が一番欲しかったものだと思う。

本リリースで作る機能
・小さく試せる参加形式（オンライン雑談枠・体験1ゲームのみの参加）
・選んだ後の温度差フィードバック・レビュー機能
・「お気に入り」「常連化」機能(一度遊んだ相手と再びつながりやすくする継続的機能)
・レコメンド機能(温度感・好きなゲーム傾向からのマッチング提案)
・通報、ブロックなどの安全機能の強化

温度感タグの位置づけ(補足)
・～じっくり系～:勝敗や戦略をじっくり考えながら遊びたい、
  静かめの雰囲気を好む人向け
・～ワイワイ系～:会話や雰囲気を楽しみたい、パーティーゲーム中心で
  気軽に遊びたい人向け
・プロフィールの温度感は本人の基本的な好み、募集ごとの温度感は
  そのイベント固有の想定(主催者が設定)であり、両者は別に管理する
・温度感が異なっていても応募は可能(足切りにしない)
・温度感が一致していても「絶対に合う」ことは保証しない。
　保証するのは「大きく外れた場になる可能性が低い」という
　期待値のすり合わせのみであり、実際のミスマッチ対策は
　タグの精度ではなく「双方またやりたい制」で吸収する


8. このアプリの懸念点とその対策
それに対して、全員に向けてではなく、痛みが強い人にピンポイントで届けることが最優先の対策

懸念点①
何が問題になりそうか：代替手段で十分うまくいかない可能性
なぜそう思うか：痛みは、実在するが、既存の手段で「我慢できるレベル」まで解決しているから
そのために考えている対策：「見るだけで応募できる」「温度感タグで事前に絞れる」
「気軽に試せる」＋「行く前に相性がわかる」の二つが、既存の手段にはない使う理由になる
###懸念点②

何が問題になりそうか：リリース直後、募集が0件の状態でユーザーが訪れる可能性
なぜそう思うか：母数が少ないと初回体験(見て応募する)が機能しないから
そのために考えている対策：初期当行とコミュニティ連携で空に見えない

###懸念点③
何が問題になりそうか：見知らぬ人同士が実際に会う前提のサービスとして危険の可能性
なぜそう思うか：深い関係を築く設計が悪用・トラブルのリスクも高めるから
そのために考えている対策：小さく試せる参加方式で段階的にリスクを下げる

###懸念点④

何が問題になりそうか：温度感タグ(じっくり系/ワイワイ系)だけでは、実際に会った時のミスマッチを防ぎきれない
なぜそう思うか：温度感は本人の自己申告であり、主観的な判断に頼っている。「じっくり系」のつもりでも、実際の振る舞いは人によって基準が違うため、タグを見て応募しても、会ってみたら合わないということは普通に起こりうる。「温度感を確認する→応募する→仲良くなる」という直線的な流れは、タグが正確であることを前提にしすぎている
そのために考えている対策：「仲間探し」をいきなりゴールにせず、「お試し参加」を中心に据える。
・温度感タグは"仮説"程度の位置づけに格下げし、応募後はいきなり継続的な関係を目指すのではなく、1回限定・低コストな参加形式(オンラインで1ゲームだけ、短時間の雑談枠など)を挟む。
・お試し参加のあとで、双方が「また遊びたいか」を答える場を設け、そこで初めて相性を判断する。双方が「また遊びたい」と答えた場合のみ、継続的な関係に進む設計にする。
→タグの精度を上げて外れを防ごうとするのではなく、外れていても被害が小さい構造にすることで対応する。

10. 技術スタック（手段としての技術）

10-1. 使用予定の技術
フレームワーク：Ruby on rails
DB：MySQL　→ PostgreSQL
デプロイ先：Render → Render + Neon 
使用予定ライブラリ：devise pagy

**変更理由**
- 当初はMySQL + Renderで進めていたが、RenderはマネージドMySQLを提供しておらず、
  MySQLをPrivate Serviceとして自前ホストすると月額$14.25が必要と判明
- 無料で使える組み合わせを探した結果、Neon(PostgreSQL)が期限なしの無料枠を
  提供しており、Renderの無料Web Serviceと組み合わせれば完全無料でデプロイできることが分かった
- これを踏まえ、DBエンジンをMySQLからPostgreSQLに変更し、
  開発・本番ともにPostgreSQLへ統一する方針に決定した
  
10-2. 技術選定の比較検討
| Ruby on Rails | 採用 | 今回の卒業制作の的間として作成したいため |
| React | 不採用 | 情報が豊富だが、まとめとしてRUby on Railsで作成したかっため |

・今回チャレンジしたい点：まとめとして掲示板アプリを一人で作成したい
